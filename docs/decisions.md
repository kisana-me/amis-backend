# 設計判断の記録

## 1. Amis を恒久的に別サービスにする

- Amis は `amis_*` の 19 テーブルと約 4,700 行のコードにまとまっていて、体験版ゲストの仕組みも自前で持っているので、本体から切り離しやすい
- AI のストリーミングとリアルタイム配信が中心で、Durable Objects に置き換えやすい。ffmpeg や mecab のような Workers で動かないものにも頼っていない
- 失敗しても SNS 本体には影響しない。D1 や DO の運用を試す場にもなる

## 2. 本体の DM AI 機能は廃止する

本体の AI 系のテーブルとコードを Amis が引き取れるので、境界から AI モデル・クォータ・利用記録を共有する話がなくなる。

## 3. 最初から D1 で作り、一括で切り替える

本体の MariaDB の `amis_*` テーブルを Hyperdrive 経由で使いながら、エンドポイントを 1 本ずつ切り替える案もあった。しかし次の理由で採らなかった。

- 1 本ずつの切り替えは、Rails と Worker が同じ DB を共有することが前提になる。最後に D1 へ移すときに、もう一度全体を切り替えることになる
- Amis は一度に切り替えられる規模である
- MySQL と SQLite の両方で動くクエリを書かなくてよくなる

## 4. ORM は Drizzle (Kysely は使わない)

Kysely を考えたのは、上の「MariaDB を経由する段階」で同じクエリを両方の DB で動かすためだった。その段階がなくなったので、Kysely を選ぶ理由もなくなった。本体の accounts / sessions は 2〜3 本の SQL を直接書けば足りる。

D1 だけなら、Drizzle でも `prepare().bind()` を直接書く方法でも作れる。テーブルが 20 を超え、JSON カラムも多いので、スキーマから型とマイグレーションを作れる Drizzle を選ぶ。

## 5. 配信は WebSocket ではなく SSE

今の `Amis::ChatChannel` は、サーバーからクライアントへの一方向の通信しかしていない (snapshot → 差分 → done)。キャンセルは別の POST になっている。それなら SSE で足りる。

- 生成を Worker のリクエストの中でやると、生成がクライアントの接続に縛られる (リロードで止まり、続きを受け取れない)。そのため生成は DO の中で行い、SSE は DO から配るだけにする
- SSE をつないでいるのは生成中の数秒〜数分だけなので、WebSocket Hibernation (長くつなぎっぱなしにしたときの課金を抑える仕組み) はいらない
- ネイティブアプリの Bearer 認証に合わせて、クライアントは `EventSource` ではなく `fetch` でストリームを読む

## 6. コインは internal API を通す (Hyperdrive で直接書かない) — 廃止

**Amis でコインを使わないことにしたので、この判断は使わなくなった** (boundary.md の「利用の制限」)。以下は当時の記録。


- 本体の `CoinService` は「行をロック → 残高を確かめる → `coin_transactions` に記録」を 1 つのトランザクションでやっている。Amis が SQL で直接書くと同じ処理を 2 か所で持つことになり、食い違ったときにお金の数字が合わなくなる
- 本体が D1 に移ると、Hyperdrive で直接書く方法は使えなくなる。API なら実装を本体 Worker に移すだけで済み、Amis は変えなくてよい
- 呼ぶのは 1 メッセージにつき 1 回で、そのあと AI の応答に数秒かかる。API を挟む遅れは気にならない

## 7. 通報は Amis 側で持つ

通報を受けたあとの対応 (ロック、`mod_rating` の上書き) は Amis の DB に対する操作なので、通報だけ本体に残しても本体からは対応できない。

## 8. 既存のゲストは切り捨てる — 体験版ゲストそのものを廃止

その後、体験版ゲストの機能ごと廃止することにした (結末とコインも同じく廃止)。以下は当時の記録。


体験版なので引き継がない。そのため、本体の Rails セッション cookie (`_amiverse`) を Amis で復号する必要もなくなる。

## 9. 本体アカウントの写しは持たない

最初は、作者が削除されたコンテンツを一覧から除くために、本体アカウントの写しを D1 に持つ案だった (D1 から取ったあとで除くと、1 ページの件数がずれるため)。

しかし本体の一覧は、そもそも作者のアカウントの状態で絞り込んでいない (コンテンツ自身の `status` と `visibility` だけ)。削除されたアカウントのコンテンツは purge で片付けている。本体と同じ動きにするなら写しは要らず、作者の表示は 1 ページ分をまとめて Hyperdrive で引けば足りる。写しを持つと、本体からの変更イベントと書き換えの処理が増え、古い値を見せる時間もできるので、持たないことにした。

## 10. セッションの検証は Amis の中で SQL 1 本 (Auth Worker もキャッシュも作らない)

最初は、本体の暗号化 Cookie を復号し、bcrypt の照合結果をキャッシュする Auth Worker を作る案だった。しかし本体のほうでサインイン Cookie を作り直した (`amiverse-docs` の `session-cookie.md`)。

- トークンは十分に長いランダム値なので、bcrypt はいらない。`token_lookup` (SHA-256 の先頭 36 文字) が一致すれば照合は終わり
- Cookie の中身はトークンを `.` でつないだだけになり、`secret_key_base` がなくても読める

そのため、検証は Hyperdrive で SQL を 1 本投げるだけで済む。わざわざ別の Worker に分けたり、キャッシュでログアウトの反映を遅らせたりする理由がなくなった。本体に毎回問い合わせる案も、Rails に頼らない体制にするという目的に合わないので採らなかった。

## 11. 生成は SSE のリクエストの中で動かす (DO も Queue も使わない)

当初は Durable Objects で生成と配信を持つ設計だった。Queue で生成して D1 経由で配る案もあった。どちらも、クライアントが切断しても生成を最後まで続けられる。

しかし MVP では仕組みを増やさないことを優先し、SSE のリクエストの中で生成することにした。代わりに次を受け入れる。

- クライアントが切断してから 30 秒を超える生成は打ち切られる (`ctx.waitUntil()` の上限)。打ち切られたものは stalled として失敗に倒す
- 別のタブやリロードした画面は、生成している接続から直接ではなく、D1 に 1 秒ごとに書かれる途中経過を読む

生成の処理は 1 か所 (`src/generation/run.ts`) にまとめてあるので、困ったら DO か Queue に移せる。

## 12. 章とクリアも廃止する (結末・実績に続けて)

結末を廃止したあとも、章の進行とクリア (`@@cleared`、チャットの完結と後日談、プロットの `clears_count`) は残していた。しかし結末が無いと最終章をクリアしても行き先が無く、章はモデルに「ねらい」を追わせるための仕組みでしかなくなっていた。そのぶんプロンプトの区画、メタ行の判定、章ごとの要約、作者の編集画面が要るので、まとめて外した。

- すべてのチャットが、今までの「章なし (free_form)」の動きになる。会話が伸びたらローリング要約で古いぶんを畳む
- プロットの人気順は、クリア数の代わりにいいね数で並べる
- `chats.status` の `finished` (1) は欠番にする。本体から移すときは `normal` に戻す
- 本体から移すとき、章ごとの要約は捨てる。畳んだ位置を持っていないので、次の生成でローリング要約として畳み直される
- モデルが古い癖で `@@cleared` / `@@ending` を書いてきても、知らないメタ行として読み捨てる

## 13. ローリング要約は 1 本ずつ走らせ、溜まったらまとめ直す

要約は生成のあとに `waitUntil` で走るので、要約が終わる前に次の生成が終わると、同じ範囲を二重に畳みうる。また、要約は追記するだけだったので、長いチャットほど「これまでのあらすじ」が際限なく伸びていた。

- チャットの `meta.summary_started_at` をリースにして、条件付きの UPDATE で取れた実行だけが上流を呼ぶ。取れなければ何もしない (二重に原価をかけない)。落ちた実行が握ったままにならないよう、5 分で期限を切る
- 期限切れで追い越された場合に備えて、書き込みは `summarized_upto_id` が読んだときのままのときだけにする
- 要約が 6 本を超えたら、新しい 3 本を残して古いものを 1 本にまとめ直す。最近の出来事は細かく、古い出来事は圧縮された形で残る。まとめ直しに失敗したら畳んだぶんだけを書き、次の実行でまとめ直す
- 畳む頻度は本体の値 (41 通で 17 通を畳む = 約 8 往復ごと) から、80 通を超えたら末尾の 30 通を残して畳む (約 25 往復ごと) に変えた。要約の料金より、畳むたびに system プロンプトが変わって次のターンのキャッシュが全損するほうが重い。畳まない間の会話はキャッシュに乗るので、細かく畳むより、溜めてまとめて畳むほうが安い。1 本が受け持つ範囲が広がったので、要約の上限は 400 字から 600 字にした
- DO や Queue で直列化する案もあったが、要約のためだけに仕組みを増やすほどではないので採らなかった (11 と同じ理由)
